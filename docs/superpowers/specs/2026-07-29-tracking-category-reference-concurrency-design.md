# Tracking 分类引用并发一致性设计

## 1. 背景

Tracking 的 Item、Subscription、Wish 都通过 `category_id` 引用分类。分类采用逻辑删除，
业务表未建立能够表达“只能引用有效分类”的数据库外键。

当前实现虽然会在业务对象创建、更新时校验分类，并在删除分类前检查是否被引用，但两组
操作之间没有共同的并发协议：

1. 创建或更新先读取有效分类；
2. 分类删除同时检查无引用；
3. 两个事务各自继续提交；
4. 最终可能出现有效业务对象引用已删除分类。

恢复链路还有一层额外语义：Item、Subscription、Wish 删除后 60 秒内可以恢复。如果分类
删除只检查 `del_flag = 0`，那么业务对象删除后、恢复窗口结束前，分类可以先被删除，随后
恢复会制造孤儿引用。

此外，Item 和 Subscription 的分页数据查询会连接有效分类，计数查询却没有同样的约束。
一旦历史数据存在孤儿引用，接口可能出现 `total` 大于实际返回条数的可观察不一致。

## 2. 目标与非目标

### 2.1 目标

- 分类删除与 Item、Subscription、Wish 的创建、变更分类、恢复并发时，不产生有效孤儿引用。
- 删除后仍处于 60 秒恢复窗口内的业务对象继续占用分类。
- 三类业务对象使用同一套分类解析、锁定和恢复窗口语义。
- Item、Subscription 的列表结果与 `total` 使用相同的数据可见性条件。
- 用 MySQL 8.4 Testcontainers 覆盖真实行锁和事务竞态；常规单元测试不依赖开发机中间件。
- 不把不可删除的系统默认分类变成所有默认写入的串行热点。

### 2.2 非目标

- 不增加或修改外部 API、错误码、状态机、表结构和跨服务契约。
- 不自动修复可能已存在的历史孤儿数据；缺少权威的重新归类规则时，静默改写数据不安全。
- 不将 Tracking 内部协议下沉到 Common。
- 不借本次任务开展全仓架构治理或引入新中间件。

## 3. 权威约束

- 系统分类 `UNCATEGORIZED` 不允许删除。
- 已被引用的自定义分类删除时返回既有错误 `BIZ_CATEGORY_IN_USE`。
- Item、Subscription、Wish 的恢复窗口统一为 60 秒。
- 恢复窗口内恢复必须成功，且不得恢复提醒。
- 恢复令牌在 `now == expiresAt` 时仍有效，因此分类引用占用区间也必须包含精确截止时刻。

由此得到恢复占用条件：

```text
active reference
OR
(deleted reference AND delete_time >= now - 60 seconds)
```

## 4. 候选方案

### 4.1 仅修正分页 COUNT

只能隐藏部分读侧表现，无法阻止新孤儿数据，也不能修复恢复竞态，拒绝。

### 4.2 增加普通外键

普通外键只能保证父行存在，无法表达父行 `del_flag = 0`。若用生成列、复合键或冗余有效
状态模拟，会引入 DDL、双写状态和迁移复杂度，且仍要处理恢复窗口，不适合当前语义，拒绝。

### 4.3 分类版本号或乐观 CAS

子对象写入仍需要对分类的“有效状态”建立提交前保留；让每次引用写入递增分类版本会制造
无业务意义的热点和冲突，复杂度高于行锁协议，拒绝。

### 4.4 对所有分类统一加行锁

正确但性能不优。`UNCATEGORIZED` 永不可删除，对它加锁会把同一用户大量默认分类写入串行化，
拒绝这种不必要的热点。

### 4.5 自定义分类行锁协议

对可删除的自定义分类建立统一悲观锁协议；系统分类只验证、不锁定。分类删除与所有会创建
有效引用的入口竞争同一行锁。协议简单、数据库原生、无需 DDL，并且锁粒度为单个用户的单个
自定义分类，采用此方案。

## 5. 设计

### 5.1 `RestoreWindowPolicy`

在 Tracking 内新增单一恢复窗口策略，持有稳定的 60 秒 `Duration`，至少提供：

- 根据删除时间计算恢复截止时间；
- 根据当前时间计算“仍可恢复”的最早删除时间；
- 判断令牌或删除记录是否仍在窗口内。

Item、Subscription、Wish 和分类引用查询全部复用该策略，移除各 Service 中重复的魔法常量。
策略属于 Tracking 业务语义，不进入 Common，也不扩展运行时配置。

### 5.2 `CategoryReferenceResolver`

在 Tracking 应用层新增分类引用解析组件，成为 Item、Subscription、Wish 所有有效引用入口的
统一依赖：

- 请求未指定分类：获取或创建 `UNCATEGORIZED`。系统分类不可删除，不加行锁。
- 请求显式指定分类：先执行非锁定有效分类查询，辨别系统分类与自定义分类。
- 自定义分类：随后执行带 `FOR UPDATE` 的有效自定义分类查询，锁定到当前事务结束；若两次
  查询之间分类已删除，则按不存在处理。
- 系统分类：确认它是当前用户的有效 `UNCATEGORIZED` 后直接返回，不执行锁定查询。
- 分类不存在、已删除或属于其他用户：保持既有 `RES_NOT_FOUND` 语义。

自定义分类正常路径多一次只读查询；这是为了避免数据库在按主键检查 `system_code` 谓词时仍
触及并锁定系统分类记录。默认分类是高频路径，消除其事务级行锁优先于少一次自定义分类查询。

### 5.3 分类删除

删除流程调整为：

1. 按用户与分类 ID 查询有效分类并执行 `FOR UPDATE`；
2. 拒绝删除系统分类；
3. 使用统一恢复窗口策略计算截止下界；
4. 检查三个业务表中是否存在有效引用，或删除时间仍在恢复窗口内的引用；
5. 有引用则返回 `BIZ_CATEGORY_IN_USE`，否则逻辑删除分类。

所有会新增有效引用的操作必须先取得同一自定义分类行锁。因此分类删除和引用写入只能串行
提交：

- 引用写入先获得锁：写入提交后，分类删除能看到引用并拒绝；
- 分类删除先获得锁：删除提交后，引用写入无法再解析到有效分类并拒绝。

### 5.4 接入范围

以下入口必须调用 `CategoryReferenceResolver`：

- Item：创建、变更分类、恢复；
- Subscription：创建、变更分类、恢复；
- Wish：创建、变更分类、恢复；
- Wish 购买：从 Wish 的分类创建 Item 前再次解析并锁定分类。

仅修改非分类字段且不会重新激活记录的操作无需获取分类锁。删除业务对象只减少有效引用，
也无需分类锁。

恢复流程先校验令牌和业务对象状态，再解析并锁定原分类，最后执行条件恢复。提醒仍保持删除
状态。若分类已在恢复窗口结束后合法删除，恢复按既有不可恢复/分类不存在语义失败，不创建
孤儿引用。

### 5.5 锁顺序与死锁分析

业务操作已有的幂等记录、业务对象锁可以先于分类锁；分类删除只锁分类行，引用检查使用一致性
读，不反向锁业务对象或幂等记录，因此不存在“分类 → 子对象”与“子对象 → 分类”的循环等待。

同一事务需要多个分类时，必须按稳定顺序获取；当前接口一次只会解析一个目标分类，不产生
多分类顺序问题。

### 5.6 查询与索引

分类占用检查分别利用现有 `(user_id, del_flag, category_id)` 索引定位有效/已删除分支，
`delete_time` 作为已定位小集合的残余条件。M1 数据量和查询形态下不新增索引，避免为低频分类
删除增加三张高频写表的索引维护成本。

Item、Subscription 的列表 COUNT 增加与数据查询相同的有效分类连接条件。它不是并发正确性的
替代品，而是对历史异常数据的读侧防御，保证 `total` 与可返回数据集合一致。Wish 已满足该条件。

## 6. TDD 与验证

### 6.1 单元测试

- 分类解析：默认分类、自定义分类加锁、显式系统分类、缺失/已删除/越权分类。
- 分类删除：先锁行；有效引用阻止删除；恢复窗口内删除记录阻止删除；窗口外允许删除。
- 三类业务 Service：创建、变更分类、恢复均通过统一解析器。
- 恢复窗口边界：精确截止时刻仍有效，超过截止时刻失效。
- Item、Subscription 分页查询与 COUNT 条件保持一致。

### 6.2 MySQL 8.4 并发测试

使用 Testcontainers 和独立事务制造确定性竞争，覆盖分类删除分别与以下操作并发：

- Item、Subscription、Wish 创建；
- Item、Subscription、Wish 变更分类；
- Item、Subscription、Wish 恢复。

测试在释放行锁后等待两个事务完成，并验证：

- 操作结果允许“一方成功、另一方按既有业务错误失败”，但不允许双方成功后留下孤儿；
- 不存在有效业务对象引用已删除分类；
- 恢复窗口内分类不能删除；
- 列表条数与 `total` 一致。

测试先在当前实现上执行并确认 RED，再实现协议并确认 GREEN，最后重构重复代码并执行回归。

## 7. 交付与回滚

按独立可审查单元提交：

1. `docs(tracking): 设计分类引用并发一致性`
2. `fix(tracking): 闭合分类引用并发一致性`

若实现需拆分，测试与实现仍应保持每个提交可编译、测试通过，不提交长期 RED 状态。

本次不含 DDL，回滚为回退实现提交。回退会重新暴露竞态，因此仅可作为紧急代码回滚；历史数据
审计采用只读 SQL 单独执行，发现异常后必须依据明确的数据修复方案处理，不在应用启动时自动改写。
